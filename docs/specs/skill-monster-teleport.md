# Monster teleport

**Description**

Monsters use teleport skills to change position immediately. Direct teleport chooses a destination from the monster's stored target point; imp teleport can instead move onto another unit or leave an attachment. The server also marks the monster for an update and changes attachment state, with collision, AI and complete synchronization limits stated below.

## 1. Scope

This contract covers server action selectors 98 and 129: destination/target selection, local relocation requests and return handling, actual collision search and map mutations, same-room/cross-room position and chain writes, update collection, attachment/cleanup decisions, the reached attachment AI initializer and persistent following. It consumes skill dispatch rather than choosing when AI should teleport. Complete link-stat propagation, remaining AI alternate/think branches, death execution and nonempty-client synchronization retain their named integration boundaries. A supplied operation result proves its caller's decisions, not that operation's unverified effects.

## 2. Trigger and ownership

D2Game owns both callbacks. [SCD-R06](skill-cast-start-and-do-dispatch.md) selects the action callback from the prepared Skills `srvdofunc` selector. The callback runs synchronously within that action; no independent periodic cadence is established. Start/mode/AI eligibility remains the dispatch owner's boundary, including SCD-Q04 for complete monster triggering. Teleport synchronization depends on the relocation operation; MTP-R21 establishes departing-client remove commands and actual pending queue writes, while complete arriving-client serialization remains unresolved.

R28/R29/R30 begin at invocation of the installed attachment thinker, after its caller selected that function. They establish the stated missing-counterpart fallback, present-counterpart idle decision and stated skill-request prefix through actual AI-control, seed, event and skill/path writes; outer event cleanup, future execution and other AI/death paths retain Q03.

R31 begins at the selected mode-8 initializer's actual start-validator invocation and ends at its return. It does not establish the preceding mode effects or a later action.

## 4. Rules (execution order)

**MTP-R01** Named selectors [verified in 1.13c data]. The named text cells in section 3 associate MonTeleport with action selector 98 and Imp Teleport with selector 129. They do not prove either action executed.

**MTP-R02** Attachment selector identity [verified in 1.13c data]. Imp Teleport's `aurastate` text cell is `attached`; the effective States row `attached` has explicit id 143. The matching reported original profile's compiled skill 330 stores `aurastate = 143`, and compiled state 143 stores identity 143. This verifies those named scalar correspondences, not gameplay execution. The helpers' fixed use of 143 is a separate code binding in MTP-R12. The effective States cell `attached.srvactivefunc` is 147 and a 2026-10-30 compiled record independently stores 147 in that field; neither scalar read establishes event execution. A separate 2026-10-30 compiled state-98 record has the consumed disguise flag clear (C05); compiled monster 492 has ordinary AI identity 122 (C06), binding R20's nondisguise path and R22's normal table selection for that captured profile.

**MTP-R03** Target-aware validation [verified in 1.13c code (static)]. For selector 129, test signed skill identity first: negative or at least skill count returns 0 without accessing a skill record. Resolve the prepared record and return 0 if that resolution is absent. Otherwise read signed 16-bit `aurastate`. Negative or at least state count returns 0 before any target, relocation or attachment operation. A valid selector reaches the first relationship lookup for `(game,caster)`, then the routing rules below. The validation stage draws no random number and writes no gameplay state. Complete prepared-record storage under GDA-R11a supplies records for valid indices; absent resolution at an in-range index is a synthetic malformed-storage case. A valid `aurastate` is a gate here; it does not replace the helpers' fixed state 143.

**MTP-R04** Direct teleport request/result [verified in 1.13c code (static)]. For a present monster with a dynamic path, read stored target X then Y as unsigned 16-bit values and get the current room. Search that room first, then its adjacent rooms in stored order, skipping absent entries, for the first signed half-open rectangle containing the point. Rectangle upper bounds use i32-wrapped origin+extent. An absent initial room yields no match. If no match, a monster with present monster data, AI control and saved lookup context resolves the control's stored kind/id in that context's registry; a found unit supplies its current room directly, without another containment search in this caller. Otherwise destination room stays absent. The producer/meaning of that saved control context is outside this supplied-input consumer.

Request relocation `(game,caster,point,destinationRoom,skipNearbySearch=false,alternateMarker=false)`. Zero returns 0 without the caller's additional update or teleport-condition write. Nonzero requests update collection (MTP-R13), sets the caster's teleport-changed condition, then returns exactly 1. The relocation operation may have its own effects before either return; zero is not a rollback. This rule draws nothing directly. MTP-R10 owns its local relocation stage; collision/general movement/client integration remains MTP-Q02.

**MTP-R05** Linked-caster route [verified in 1.13c code (static)]. After MTP-R03 succeeds, resolve the caster relationship (MTP-R08), refresh its cached target (MTP-R09), read that cache and treat self as absent. If the saved relationship is present, request coordinate resolution (MTP-R09), then relocation with the produced point, no supplied room, `skipNearbySearch=false` and `alternateMarker=false`, then cleanup `(game,caster,saved counterpart,invocation skill identity)` under MTP-R12. Return exactly 1 after those calls return normally. Both the coordinate resolver's boolean result and the relocation result are ignored; the produced coordinates are still forwarded. Cleanup takes the skill identity, not the invocation level. No direct draw. Complete downstream effects remain MTP-Q02/MTP-Q03.

**MTP-R06** No-target fallback [verified in 1.13c code (static)]. After the relationship and target refresh above, with no caster relationship and no distinct cached target, delegate to selector 98 with the invocation game, caster, identity and level; return its result unchanged. No target-alive test or attachment request occurs on this branch. No direct draw. The direct stage's integration limits remain MTP-Q02.

**MTP-R07** Distinct-target route [verified in 1.13c code (static)]. With no caster relationship and a distinct refreshed target, first resolve that target's relationship; a present result returns 0. Otherwise reject when its alive-exclusion condition is set, its kind is neither player nor monster, or its mode is player 0/17 or monster 0/12. A target with a relationship condition set but an unresolved counterpart passes the relationship test. For a surviving target, obtain X, Y and current room in that order; dynamic X/Y use NRF-R10b, with the local wrappers returning 0 for an absent dynamic path. Request relocation using that point/room with `skipNearbySearch=true` and `alternateMarker=false`. Zero returns 0; nonzero requests attachment `(game,caster,target,invocation identity,invocation level)` under MTP-R12, then returns exactly 1. Attachment can decline its own family checks without changing this final result. No direct draw. Complete relocation/link/AI effects remain MTP-Q02/MTP-Q03.

**MTP-R08** Relationship resolution [verified in 1.13c code (static)]. An absent unit or clear relationship-present condition yields absent without registry lookup. Otherwise resolve its stored counterpart kind/id in the supplied game's registry and return that unit or absent. This consumer does not set a relationship or infer one from state membership. R26's saved-owner wire field reads this same relationship-present condition and saved counterpart kind/id. Valid registry kinds are 0..5; malformed stored kinds are outside this rule. No write or draw.

**MTP-R09** Target refresh and coordinates [verified in 1.13c code (static)]. With present game, caster and path, refresh does nothing when the cached target is absent. Otherwise resolve the path's saved target kind/id in the game registry. If the resolved reference differs from the cached reference, clear only the cached reference. Independently, a resolved item in mode 1 or 2 also clears that reference. Clearing preserves the saved kind/id; refresh never replaces a stale pointer with the resolved unit.

Coordinate resolution first performs that refresh, then reads the cache. For a distinct present target, get its X then Y: objects/items/tiles read their prepared static coordinates; other kinds use dynamic integer position parts, or 0 per coordinate when the target path is absent. For absent/self cache, read the caster's stored target X then Y. Write both output coordinates before returning 1 when both are nonzero, otherwise 0. No direct draw. Missing game/caster/path and invalid registry kinds are outside the valid-input stage.

**MTP-R10** Monster relocation local stage [verified in 1.13c code (static)]. With a present monster and dynamic path, retain its old room. Use a supplied destination room, or search the old room and its stored adjacent rooms using MTP-R04's rectangle test. No room returns 0. Unless `skipNearbySearch`, obtain the unit collision footprint and request the nearby-position operation with room, mutable point, footprint, mask 7177, scan limit 50 and fixed search controls 0/1; use its returned room and point. An absent returned room returns 0. MTP-R15 produces that footprint and exact search result.

Request the path relocation operation with path, caster, selected room and the low unsigned 16 bits of each point coordinate. Zero returns 0. Nonzero requests update collection, sets the ordinary teleport-changed condition when `alternateMarker=false` or the alternate relocation-changed condition otherwise, requests room/client synchronization, and returns 1. The synchronization helper immediately does nothing for a monster path whose room-synchronization condition is clear. With a set synchronization condition, distinct present old/current rooms and empty client collections on both rooms, it clears the monster room-transition auxiliary reference and the path synchronization condition without emitting a request. MTP-R21 establishes the remaining recipient merge and departing-client pending writes; arriving-client creation-message effects remain MTP-Q02. This stage draws nothing directly; dependency effects/draws are separate. MTP-R16/MTP-R17 establish actual collision, position and room writes; MTP-R11 retains its isolated same-room suffix.

**MTP-R11** Reached same-room position commit [verified in 1.13c code (static)]. This suffix begins after collision-footprint operations have returned normally, with a monster dynamic path, selected room equal to its current room, its room-update-request condition clear and its containing-room guard clear. The selected point is within that room. Let X and Y be the unsigned low 16 bits supplied to path relocation. Store centered 16.16 positions `FX=u32((X<<16)+32768)` and `FY=u32((Y<<16)+32768)`. Store projected path components `A=sar(i32((FX>>>11)-(FY>>>11)),1)` and `B=sar(i32((FX>>>11)+(FY>>>11)),2)`. The unsigned shifts precede the signed additions/subtractions. Snap again to the same centered coordinates, clear the moving condition, set both path progression counters to 0 and set the two path auxiliary reset values to 0; return 1. No room transfer, draw or event request occurs in this suffix. It verifies these actual stored fields at this reached boundary; the complete collision/position operation is MTP-R16. Wider meanings of the auxiliary reset values are not asserted.

**MTP-R12** Attachment and cleanup local decisions [verified in 1.13c code (static)]. Both helpers first require a present caster and counterpart, caster base family 492 within the loaded monster count, and counterpart base family 435 or 441 within that count. Other families return without state/link/event/AI requests. The base-family getter returns -1 for a non-monster; for a monster with a valid prepared MonStats record it reads signed `BaseId`, otherwise its class identity is returned and then checked by the helper's bounds.

Attachment requests, in order: state 143 on for the caster (RLI-R03/STL-R07); link caster to counterpart; link counterpart to caster; remove caster type-5 events whose key equals the invocation skill identity (key 0 removes all type-5 events); allocate/link a new caster event. With a supplied successful event allocation and valid queues, set event kind 5, frame -1, key/first parameter equal to skill identity, second parameter equal to level and no override; insert it at the front of the monster persistent-event queue as well as the unit chain. Clear caster interaction conditions A/B/C, then request its AI-control change with selector 16. MTP-R18 establishes the reached attachment initializer and MTP-R19 the persistent following event. Complete link propagation, other AI installation/execution and death retain MTP-Q03.

Cleanup requests state 143 off, unlink caster, then unlink counterpart, in that order. Evaluate caster health percentage under MTP-R14. If it is below 10, request caster death with absent attacker and control 1 and stop this helper. Otherwise set interaction conditions A/B/C, remove its type-5 events using the supplied skill identity as key (0 again means all), and request AI-control selector 0. Death execution is MTP-Q03. Neither helper performs a direct draw outside its dependencies.

The link operation's verified immediate prefix stores the counterpart kind/id before any optional state/stat integration; unlink stores zero in both saved fields before that integration. Other supplied state-98 list kinds and disguise-true integration remain MTP-Q03; MTP-R20 closes the ordinary producer path. Event allocation uses a free-node pool. During growth with a valid present existing pool head and no free node, if the new-pool resource request returns absent normally, the first attempt to link through that absent new-pool result reaches an invalid-memory-access fault. There is no ordinary attachment/callback result on this reached path, and earlier state/link effects and completed event-removal processing precede the fault without rollback. Subsequent exception handling or process termination is outside this fault-boundary contract. MTP-R20 establishes actual effects for the ordinary source-unit lists this producer creates. Supplied normal-return link operations in stage fixtures still verify only the caller order and arguments.

**MTP-R13** Update collection [verified in 1.13c code (static)]. With a present unit, get its current room. No room, a room's update-suppression condition, or an already-set unit queued condition makes no change. Otherwise set the unit queued condition, set the room changed marker, set the unit's next-update reference to the room's prior update head and make this unit the new head. Valid room queue storage is required. Repeated collection of an already-queued unit does not move it to the front again. This is collection only, not client delivery. No draw.

**MTP-R14** Cleanup health percentage [verified in 1.13c code (static)]. Obtain raw signed i32 stat 6 then stat 7 through the shared stat reader. For supplied returned values H and M, compute `h=sar(H,8)` and `m=sar(M,8)`. If m=0 return 0. Otherwise return signed `truncTowardZero(i32(h*100)/m)`. No clamp is applied; multiplication wraps before division and numeric-foundation division faults retain their contract. No draw. Actual stat aggregation is consumed from RLI-R02a/RLI-R02b; these supplied values do not verify a missing producer.


**MTP-R15** Teleport collision search [verified in 1.13c code (static)]. For a monster, resolve its MonStats record, then signed `MonStatsEx` into MonStats2; an invalid index or absent extended record gives footprint 0, otherwise read `MonStats2.SizeX` as signed i8. This consumes the supplied prepared collections, not a named monster's unobserved numeric value.

The nearby search used by teleport takes a present mutable point, no reference/line-of-sight point, mask 7177, limit 50 and step 1. Test the original point first. A candidate is acceptable only when its containing room is found by MTP-R04's ordered rectangle search and its collision test is zero. Footprints 0/1 test one cell, 2 tests center and four orthogonal neighbors, 3 tests the inclusive three-by-three square; any other signed footprint gives collision result 65535. Cells are unsigned 16-bit masks. A point query with absent room/grid/cell storage returns 39, not a mask-filtered zero. Cross queries with absent central room/grid/storage return the low 16 bits of the requested mask; unhandled cross-boundary codes likewise return that mask. For ordinary cross boundaries the code ORs the five masked cells, resolving out-of-grid neighbor cells through the current room/adjacent search; a missing such point contributes 39. Opposite-side boundary codes are unhandled. Square queries split at grid right/bottom edges and recursively OR the masked portions; a missing room/grid or invalid portion contributes 39. Square-grid cell storage is unchecked once its metadata is present; absent backing storage has no safe collision value.

If the original point fails, visit square perimeters at radii 1 through 49. At radius r, first visit y from Y-r through Y+r in increasing order, testing (X-r,y) then (X+r,y). Then visit x from X-r+1 through X+r-1 in increasing order, testing (x,Y-r) then (x,Y+r). Among acceptable points on that perimeter retain the one with smallest Manhattan distance to the original point, replacing only for a strictly smaller score. Finish that perimeter before accepting; the first tie remains selected. Stop at the first perimeter with any candidate, store its point and return its containing room. No candidate returns absent and leaves the original point unchanged. Arithmetic uses wrapped i32; the teleport's unsigned-low-word input and maximum radius keep these offsets nonoverflowing. No random draw or collision-map write occurs.

**MTP-R16** Actual monster collision relocation and position stores [verified in 1.13c code (static)]. The path supplies its collision-write pattern and mask. Pattern 0 or outside 0..5 performs no map write. Pattern 1 applies the mask to center plus four orthogonal cells, then, only for a nonzero original mask, applies 4096 to the center. Pattern 2 applies the mask to the three-by-three square and, only for a nonzero original mask, applies 4096 to the cross. Pattern 3 applies the mask to the cross and, only for a nonzero original mask, applies 8192 to the center. Pattern 4 applies the mask to the three-by-three square and, only for a nonzero original mask, applies 8192 to the cross. Patterns 3/4 do not separately apply 4096; each pattern is independent. Pattern 5 applies only the cross mask. Set means bitwise OR of the low 16 bits; clear means bitwise AND with their complement. Resolve each cell/rectangle portion using the ordered containing-room search; absent room/grid causes no write. Point/cross writes also skip absent cell storage; rectangle writes require its unchecked backing storage. These are bit operations, not occupancy reference counts.

For path relocation of a monster, when destination point is (0,0), clear the old footprint. Otherwise, only when the old room is present, clear its old footprint then set the selected room's footprint at the new point. Write patterns and masks are taken from the path, independently of the search footprint. Set the room-update-request condition if selected room differs from current room.

The shared position-store operation first checks the containing-room guard: when set, if the new integer point is not found from current room/adjacent rooms, set the second progression counter to 0 and return without position/projection/room writes. Otherwise store the supplied full 16.16 coordinates and projection under MTP-R11's formulas. With a present path owner and room-update-request condition set, execute MTP-R17 using the supplied fallback room.

Relocation calls that store with centered low-word destination coordinates. A nonzero destination must also belong to the selected room/current-adjacent search or execution takes a fatal assertion path; no safe result 0 is substituted. Then snap the path's resulting current coordinates to their half-unit centers through the same position-store operation, clear moving, reset both progression counters and both auxiliary reset values to 0, and return 1.
