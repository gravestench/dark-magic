# Monster resurrection, healing and blood sucking

**Description**

Some monsters heal another creature, bring a corpse back into play, or regain life through a blood-sucking attack. These use different server actions. The healing action chooses a percentage of the target's maximum life, with a cap at maximum life; the complete resurrection and blood-sucking effects remain gated.

## 1. Scope

The server callbacks for ZakarumHeal/Bestow, Resurrect/Resurrect2, Self-resurrect, Mosquito and Suck Blood in the Expansion profile. This owns their local skill decisions and requested effects, including the valid healing callback's target normalization, compiled calculation requests, existing-stat reads and replacing-write request. AI choosing a skill, generic stat storage, combat execution and corpse lifecycle are dependencies. Successful resurrection and both blood-sucking action families remain MRH-Q02/MRH-Q03 rather than being inferred from callback names.

## 2. Trigger and ownership

D2Game owns these monster skill handlers. The [shared skill dispatcher](skill-cast-start-and-do-dispatch.md) selects the start/action callbacks through `Skills.srvstfunc`/`srvdofunc`; MRH-R01 gives the observed text associations. The common dispatch boundary is SCD-R03–SCD-R09c, retaining that spec's AI/frame gates. No fixed AI think cadence or client-message identity is established here. The supplied-input arithmetic begins after healing target/preparation and both skill calculations have completed.

## 4. Rules (execution order)

**MRH-R01** **Original text selectors** [verified in 1.13c data]. In effective `data/global/excel/skills.txt`, exact named cells are ZakarumHeal.`srvdofunc` = 96; Bestow.`srvdofunc` = 96; Resurrect.`srvdofunc` = 97; Resurrect2.`srvdofunc` = 97; Self-resurrect.`srvstfunc` = 61; Mosquito.`srvstfunc` = 55 and `.srvdofunc` = 107; Suck Blood.`srvstfunc` = 60 and `.srvdofunc` = 127. ZakarumHeal.`calc1` is `15+5*lvl` and `.calc2` is `50`. These named text values do not prove compiled fields, AI eligibility or calculation execution; see MRH-D01.

**MRH-R02** **Invalid healing/resurrection action id** [verified in 1.13c code (static)]. At the heal, resurrect or blood-suck action callback entry, reject a signed skill id below 0 or at least the loaded Skills count with signed result 0. This branch precedes helper calls, RNG and gameplay writes. Valid loaded table storage is assumed; other malformed-storage and target cases are not covered by this guard.

**MRH-R03** **Healing percentage and write request** [verified in 1.13c code (static)]. At the supplied-input stage, use the upper calculation result first: `upper = clamp(calc2,0,100)`. Then `lower = clamp(calc1,0,upper)`. All are signed i32. Let `range = upper-lower`; use the caster's bounded draw of NRF-R02 with modulus range, which returns 0 without stepping for range <= 0. Set `percent = lower+draw`. Thus a nonempty interval excludes its upper endpoint; equal endpoints produce that endpoint without a draw.

Read supplied target maximum life and current life. Set `increase = mulDiv(percent,maximumLife,100)` using NRF-R05 in that exact operand order. Set `candidate = i32(low32(currentLife+increase))`, then if candidate <= 1 set candidate = 1. Select `writtenLife = min(candidate,maximumLife)` using a signed comparison. Request target stat 6 `hitpoints`, layer 0, raw writtenLife, then return signed 1. The raw lower floor is 1/256 life, not one whole life; the subsequent maximum clamp can override it. There are no local RNG draws after the percentage draw. Supplied getter/write operations have no additional draws/effects in this isolated stage. MRH-R06/MRH-R07 define actual preparation, calculation requests and existing-stat reads. Actual replacing-write storage/propagation remains MRH-Q01; this gate does not block the supplied-result arithmetic.

**MRH-R04** **Resurrection and self-resurrection** [unresolved]. The resurrection action validates a selected corpse and invokes revival/mode/room operations before optional target-state handling. Self-resurrection has a separate start path and monster-type gate. Complete eligibility, corpse reuse/removal, restored state, life and ownership are gated by MRH-Q02; no assumption of full-life or player-style resurrection follows from the action name.

**MRH-R05** **Complete blood-sucking integration** [unresolved]. MRH-R09 establishes Suck Blood's monster-recipient life operation before queued combat consumption, MRH-R10 establishes Mosquito's start preparation, and MRH-R11 establishes its local action through supplied combat boundaries. Complete start/action execution, subsequent combat effects, other caster kinds and Mosquito's action remain MRH-Q03. Mosquito uses a distinct start/action pair, target identity bookkeeping, repeated damage-related draws and a caster life request. The heal percentage rule MRH-R03 is not substituted for either action.

**MRH-R06** **Healing target normalization and early rejection** [verified in 1.13c code (static)]. This rule starts after MRH-R02 admits a valid loaded skill record. Its normal-entry boundary requires a nonempty game, caster and caster path; when a target is selected, the cached type is one of the supported unit kinds 0–5 and the game registry is valid. If no unit is currently selected, normalization changes nothing. Otherwise resolve the registered unit for the cached target type/id. If that unit is absent or differs from the selected unit identity, clear selection; do not switch selection to the resolved unit. Independently, if the resolved unit is an item in mode 1 or 2, clear selection. Clearing the selected unit leaves the cached type/id unchanged. No RNG is drawn and no stat is read or written during this normalization.

Read selection after normalization. If it is absent or is the caster itself, return signed 0 before setting the do-handled latch or evaluating either calculation. Otherwise retain that selected target and proceed to MRH-R07. Normalization does not add a friendliness, living-target, distance, difficulty or monster-only target test; any such upstream eligibility belongs to its producer. Invalid game/caster/path or malformed registry inputs are outside this verified normal-entry boundary, rather than successful empty-target defaults.

**MRH-R07** **Successful healing callback through the write boundary** [verified in 1.13c code (static)]. After MRH-R06 retains a distinct nonempty target, set the caster's do-handled latch. Evaluate the loaded skill's `calc2` through SCX-R11 in context (caster, skill id, callback level), normalize its upper endpoint as MRH-R03, then evaluate `calc1` through the same front end and context and normalize its lower endpoint. Both calculations are requested, including when the normalized upper endpoint is zero. Each evaluation completes before the next step. SCX owns execution of the requested compiled expression, its parameter/function dependencies and any seed changes; those draws precede MRH-R03's bounded draw, which uses the caster seed as it stands after both evaluations.

Then perform the percentage draw and arithmetic of MRH-R03, reading the retained target's stat 7/layer 0 first and stat 6/layer 0 second through RLI-R02a/RLI-R02b. The maximum-life front end uses exactly stat 7; it does not read a separate cached maximum or infer a maximum from current life. These reads select own/resolved arrays and apply conditional minimum adjustment according to RLI; neither is necessarily an unmodified base value. Request the target stat 6/layer 0 replacing write with the computed raw result, and, if that operation returns normally, return signed 1 without testing its result. Successful callback return therefore does not establish that storage changed. Actual replacing storage, propagation and notifications consume the unresolved STL-R06c/STL-Q07 and RLI-Q03 boundary identified by MRH-Q01. Expression compiler or unresolved parameter-producer effects retain their SCX gates; explicitly supplied valid compiled expressions and existing stat arrays allow this complete callback-to-request path independently of them.

For healing, execution is MRH-R02 → MRH-R06 → MRH-R07, with MRH-R07 consuming MRH-R03's arithmetic. MRH-R04/MRH-R05 describe separate action families.

**MRH-R08** **Reached prepared life storage** [verified in 1.13c code (static)]. This consumes the shared STL-R06e replacing write and STL-R06d direct propagation through the actual unit-facing writer; it does not replace the generic STL authority. The target has a valid extended base list with state storage, no parent, secondary false (delta propagation enabled) and valid sorted own/resolved arrays. The stat-6 definition has the recorded original-profile controls: dependent expansion/formula zero, retainResolvedZero false, filteredStat false, notifyResolvedChange false, dependentMarker false and collectChangedKey true. Each life entry may independently be present or absent. The request and resulting resolved value are nonzero, and each array has room for any required insertion, with counts/capacities in 0..32767. This case needs no resize, deletion or allocation operation.

Apply STL-R06e to stat 6/layer 0, taking an absent own value as zero. Equality produces an internal unchanged result and leaves both arrays unchanged. Otherwise insert the missing own entry when needed, compute `delta = i32(low32(requestedLife-oldOwnLife))`, and store the requested value before propagating. STL-R06d starts at this extended base itself: add delta with i32 wrap to its old resolved life, taking absence as zero and inserting the missing resolved entry when needed, then stop at the absent parent. Each insertion increases only its array's count by one; capacities and backing stores remain unchanged. Unrelated entries and list relations remain unchanged. There is no clamp in this reached replacing operation. It invokes no stat callback, inserts no changed-stat key for stat 6 and draws no RNG. The internal list operation reports changed on this branch. For a player target the unit front end additionally requests changed-key bookkeeping, which excludes stat 6 without inserting it. MRH-R07 returns 1 after normal completion of either branch; no numeric return from the unit stat-writing front end is required. This also admits the same isolated unit-writer operation when another owned skill path requests it; it does not verify that path's preceding or subsequent effects. Complete other list conditions, resize/failure, propagation and later notifications remain MRH-Q01 under their shared owner.

**MRH-R09** **Suck Blood recipient and life operation** [verified in 1.13c code (static)]. This rule enters action 127 with a valid loaded skill, a monster caster, valid game/path/registries and well-formed pending combat records. Normalize selection as MRH-R06; an absent or self target returns 0 before the do-handled latch. Otherwise set that latch and walk the caster's queue from its head for the first record whose attacker type/id equals the caster and defender type/id equals the retained target. With no match, return 0 after setting the latch. Later matching records do not supply the life basis.

If that first record's hit result bit 1 is clear, skip the recipient/read/calculation/write operation. Otherwise obtain the caster's owner through its monster AI context: absent monster data, absent context, absent context game or absent registered owner yields no owner. A present context resolves its stored owner type/id against its stored game's registry, independently of the selected target. Use the resolved unit when present, otherwise use the caster. No player-only owner test is added.

In order, read recipient current life (stat 6/layer 0), recipient maximum life (stat 7), and selected target current life (stat 6/layer 0) through RLI-R02a/RLI-R02b. Set `basis = min(queuedPhysical,targetCurrentLife)` by signed comparison. Evaluate this skill's `calc1` through SCX-R11 with the caster, skill id and callback level. Do not clamp that signed result to a percentage interval. Compute `increase = mulDiv(calc1Result,basis,100)` with that exact NRF-R05 argument order, then `candidate = i32(low32(recipientCurrentLife+increase))`. Floor a candidate below raw 1 to 1, then signed-clamp it to recipient maximum life. Replace recipient stat 6/layer 0 with that value. MRH-R08 establishes actual own/resolved storage when this recipient satisfies its reached-list conditions; the general replacing-write boundary remains MRH-Q01. The local operation does not subtract life from the selected target or alter the queued record.

After this operation, or directly on the non-hit branch, invoke DPO-R13a's queued consumer with the original game, caster and selected target; return 1 after its normal completion. Thus the life replacement precedes that consumer's later reach/apply checks. No independent local RNG draw occurs; expression and combat dependencies own any draws they perform. DPO's reach, apply, callback and downstream gates remain attached to the actual consumer; this rule does not establish its final damage, removal, reflection or notification result.

**MRH-R10** **Mosquito start preparation** [verified in 1.13c code (static)]. Start 55 first rejects a negative skill identity, identity at least the signed Skills count or absent selected record with result 0. Otherwise obtain the caster's current skill node; an absent node returns 0 before target normalization. With a present node, normalize selection through MRH-R06's valid-entry operation. An absent or self target then returns 0 before calculation or node writes.

For a distinct retained target, initialize a temporary seed to `{lo: low32(casterId+targetId), hi:666}` before the calculations. It is separate from the caster and target seeds. Evaluate `calc1`, then `calc2`, through SCX-R11 in context (caster, skill id, callback level). Let their signed results be `lower` and `upper`; do not sort or clamp them. Set `range = i32(low32(upper-lower))`, draw `r = Rand(temporarySeed,range)` under NRF-R02, and set `preparedCount = i32(low32(lower+r))`. If this count is below 1, replace it with 1. Thus a positive range draws once, including range 1; a nonpositive range draws nothing. Expression-owned seed changes remain on the expression context and are not used as this local draw's seed.

Store the resulting count in the retained current node, then the retained target's id, then its type, overwriting those three fields; return 1. Other node fields and the do-handled latch remain unchanged. No life or damage operation occurs in this start. Complete subsequent Mosquito action execution and AI/frame entry remain MRH-Q03/MRH-Q04; preparing the count does not establish the number or timing of executed attacks.

**MRH-R11** **Mosquito action's damage, life and repeat operations** [verified in 1.13c code (static)]. Within a valid game, present-caster, registry and well-formed node-storage boundary, action 107 validates its skill as MRH-R10, obtains the current node, resolves that node's stored target type/id against the original game's registry, and requires the reach predicate on (caster, resolved target, extra allowance 0) to return nonzero. Missing node/registered target or failed reach returns 0 before the following draws/writes. It does not normalize or use the path's selected target. The reach producer remains the existing spatial/combat integration gate; a supplied reach result establishes only this local consumer. Retain this node and snapshot its prepared count after reach.

Clear the whole damage record. In order, request SLD's physical minimum then maximum with source inclusion 1 and arithmetic-shift each returned i32 right by 8, retaining these whole-unit endpoints. Perform SLD-R14's physical fill (source inclusion 0), then SLD-R15–SLD-R17's elemental fill, on the cleared record. Using the caster seed, take three additional NRF-R02 `Rand` draws with the same wrapped signed range `wholeMaximum-wholeMinimum`: the first sets poison magnitude to `low32((wholeMinimum+r)*2)`; then independently request SLD-R11 duration again with condition 1 and store it as poison length; the second sets mana drain to `low32((wholeMinimum+r)<<8)`; the third sets stamina drain by that same shift. These assignments replace the corresponding elemental-fill values. Each endpoint/duration/calculation and fill completes before the next step; dependency draws stay at their request positions. Then set the damage result word to hit bit 1.

Evaluate skill `calc3` through SCX-R11 with caster, callback skill id and level. Read caster current life, compute `increase = mulDiv(calc3Result,record.physical,100)` in that exact NRF-R05 operand order, and wrap-add it to current life. Read caster maximum life and signed-clamp that candidate to the maximum, with **no lower floor or percentage clamp**. Replace caster stat 6/layer 0; actual reached storage consumes MRH-R08 and general storage retains MRH-Q01. This precedes the damage-apply call.

Invoke DPO's apply operation with original game/caster/resolved target, this damage record and scale request true. On normal completion, read target current life; exactly zero ORs lethal bit 2 into the current record result, while a nonzero value does not clear or set that bit locally. Invoke HRC's reaction consumer with original game, target, caster and the current record. DPO/HRC own their actual damage, states, modes, callbacks, draws and other effects with their existing gates.

After reaction completes normally, compute the retained count snapshot minus 1. If signed positive, store that value in the **retained** node, set the caster's sequence-event value to `Param1`'s low 24 bits while preserving the sequence field's current low byte, and replace its current animation total with `i32(low32((u32(total)&0xFFFFFF00)+256))`. These use the control values current after the reaction, not values saved before it. If the decremented count is nonpositive, make none of those three writes; in particular a prepared count of 1 remains stored as 1. Return 1 after either branch. No do-handled latch write occurs in this action, and no additional local draw follows the three explicit draws. The start's positive prepared count and the retained node's valid lifetime across consumers are normal-entry preconditions. Subsequent animation/AI execution and complete generic combat effects remain MRH-Q03/MRH-Q04.

## 6. Branches and edge cases

The arithmetic uses raw signed life values and signed clamps; a zero or negative supplied maximum can override the raw lower floor. A positive range always draws once, including range 1. Negative or overlarge percentages are normalized before drawing. The upper percentage is exclusive only for a nonzero interval. NRF-R05 may divide first on large operands, losing precision; replacing it with a mathematically exact product/division changes results. Signed 32-bit addition wraps before the lower and upper clamps. The verified healing callback contains no difficulty branch; level/data and actual AI entry producers retain their SCX/MRH-Q04 limits. Corpse type and collision failure remain MRH-Q02.

## 8. Test vectors

### 8.1 Executable vectors

MRH-V02–MRH-V06 enter MRH-R03 with a valid selected target T and caster C after preparation/calculation. Supplied getter results are stable, the life-write log starts empty, the write operation logs its request without changing other state or drawing RNG, and the stage returns 1 after that request. MRH-V07/MRH-V08 instead exercise the new boundaries stated in their own inputs. Numeric life inputs/outputs are raw 8-bit-fraction values. Each case is independent. A positive draw steps only C's supplied seed; all other seeds remain unchanged.

- **MRH-V01** Invalid id before target access (MRH-R02; boundary: isolated rule)
  - Inputs: loaded count = 357; caster/target absent; level = 1; helper/write logs empty. For each heal, resurrect and blood-suck action run (a) skill id -1; (b) skill id 357.
  - Seeds: `no draw`.
  - Draws: none.
  - Trace: signed lower or exclusive upper test fails before first call.
  - Outputs: each case result = 0; helper/write logs = []; seeds unchanged.
  - Discriminates: rejects inclusive upper bounds and target/preparation work before the guard.
  - runtime_observed: no

- **MRH-V02** Nonempty interval excludes upper endpoint (MRH-R03; boundary: supplied-input stage)

  - Seeds: C = {lo: 1, hi: 666}.
  - Draws: (C, modulus 30, result 21); final C = {lo: 1791398751, hi: 0}.
  - Trace: lower 20, upper 50, range 30; percent 41; mulDiv(41,25600,100) = 10496; candidate 13056; neither clamp changes it.
  - Outputs: write log = [(T, stat 6, layer 0, raw 13056)]; result = 1; C as above.
  - Discriminates: using an inclusive 31-value interval changes the roll/result; using current life as percentage basis changes the write.
  - runtime_observed: no
